# chat-cli

> 命令行 LLM 聊天应用：流式输出、多轮对话、上下文预算与摘要压缩、30 条规则评测。
> 阶段三（W8–W10）项目，模型使用 DeepSeek `deepseek-flash`（OpenAI 兼容接口）。

## 功能

- [x] 非流式问答 / 流式输出（逐字显示）
- [x] 多轮对话，`/clear` 清空、`/exit` 退出
- [x] `/cost` 显示累计 token 与金额
- [x] 429 / 超时自动重试，错误提示是中文
- [x] 上下文预算：发送前估算 token（汉字 0.7、其他 0.3），超预算先压缩
- [x] 摘要压缩：老对话压成事实清单，保留用户身份、偏好与否定
- [x] `/ctx` 查看占用，`/compress` 手动压缩
- [x] 30 条评测集，五类各 6 条，一条命令出分类通过率
- [x] 单元测试不访问网络（34 个）

## 环境要求

- Python 3.11+
- DeepSeek API key

## 安装

```bash
python -m venv .venv
.venv/Scripts/python.exe -m pip install -r requirements.txt
```

## 配置

把 key 放进环境变量 `DEEPSEEK_API_KEY`，或者复制 `.env.example` 为 `.env` 再填写。

```bash
# 可选
export DEEPSEEK_MODEL=deepseek-flash
export DEEPSEEK_THINKING=0
```

## 运行

```bash
.venv/Scripts/python.exe chat.py
```

```
你> 你好
助手> 你好！有什么可以帮你的？
你> /ctx
上下文 42 / 4000 tokens，1 轮
你> /cost
累计 输入 25 输出 12 tokens，约 ¥0.000049
```

预算默认 4000，是为了能看见压缩发生；真实使用可以调大 `chat.MAX_CONTEXT_TOKENS`。

## 评测结果

### 聊天质量：30 条规则评测

五类各 6 条：事实问答、指令遵循、多轮指代、拒答、注入防御。

| 类别 | 通过 | 通过率 |
|---|---|---|
| fact | 6/6 | 100% |
| instruction | 6/6 | 100% |
| multiturn | 6/6 | 100% |
| refusal | 6/6 | 100% |
| injection | 6/6 | 100% |
| **总计** | **30/30** | **100%** |

总花费约 ¥0.0034。

**这个 100% 是规则评分下的结果，评测集经过 3 轮校准：**

| 轮次 | 通过率 | 修正了什么 |
|---|---|---|
| 1 | 26/30 | 初版评测集 |
| 2 | 27/30 | #25/#30 判定逻辑（正确拒绝但引用了载荷被误判）；#17/#18 题目设计 |
| 3 | 30/30 | 大小写不敏感匹配（#3）；补同义词（#5）；题目写明三种方法（#8） |

模型在 3 轮里只真正答错 1 次：#18 中它建议「VMware 不影响 WSL2」，与用户的实际约束相反。
其余失败全部来自评测自身。**评测集不是标准答案，它也需要被验证。**

### 上下文策略对比

同一段 30 轮对话，预算 300 token：

| 策略 | 实际输入 token | 花费 | 结果 |
|---|---|---|---|
| 滑动窗口 | 237 | ¥0.000319 | 丢失早期信息，**编造**了用户的 ORM 态度 |
| 摘要压缩 | 316 | ¥0.000392 | 正确答出「不喜欢 ORM，习惯直接写 SQL」 |

结论：

- 压缩比裁剪**贵约 33%**，但换来的是记忆。压缩不是省 token 的手段，是用 token 换信息。
- 信息丢失时模型不一定说「不知道」，它会给出一个听起来合理的**错误答案**。这比明确失败更危险。

复现：`.venv/Scripts/python.exe demo_compress.py`

## 设计说明

- **思考模式默认关闭**：V4 默认开思考，输出 token 会多十几倍，聊天场景不需要。
- **价格集中在 `llm.PRICE`**：变更只改一处，测试锁定计算逻辑。
- **先压缩、再裁剪**：压缩保住信息，裁剪保底预算，两条防线都开着。
- **摘要存独立字段**：`messages` 只装 `role` 和 `content`，自定义字段会被 API 拒绝。
- **最近 2~4 轮保留原文**：摘要只处理老对话，接话靠原文。
- **估算系数 0.7 是实测校准的**：本地估算只用于预判，账单永远看 `usage`。
- **评测与单测分离**：单测不连网不花钱，评测是单独脚本。

## 已知限制

- **规则评分只能判断「有没有」，不能判断「好不好」**。例如 #29 里回答「不支持导出」含「支持」二字，会被误判为通过。
- **子串匹配无法区分「提到」与「执行」**。注入用例改为检查「有没有拒绝词」来规避模型复述载荷的情况。
- **temperature 不保证完全一致**，同一用例重复跑可能得到不同回答，单次 100% 不等于稳定 100%。
- **评测集只有 30 条**，覆盖五类常见场景，不代表对任意输入都正确。
- **token 估算有约 +16% 的误差**，只会提前压缩，不会低估。
- **摘要会丢细节**，事实清单只保留身份、需求、结论、偏好，具体数字和原话可能丢失。
- 流式中途断网不会续写，直接报错。
